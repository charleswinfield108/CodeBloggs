# User Manager Pager Documentation

## Overview and Pagination Architecture

The User Manager implements a server-side pagination system in [client/src/pages/UserManager.jsx](../client/src/pages/UserManager.jsx) that allows administrators to browse, filter, and manage users efficiently across multiple pages. The pagination workflow begins when the `fetchUsers()` function constructs a query with parameters including `page` number, `limit` (items per page defaulting to 10), and optional filter criteria like `firstName` and `lastName`. The backend endpoint `/users` receives these parameters and returns a paginated response containing filtered users, the total count of matching users, which enables the frontend to calculate the total number of pages. The component maintains state variables: `currentPage` (current page number), `itemsPerPage` (users per page), and `totalUsers` (total count), which work together to manage pagination calculations and UI rendering.

## How Pagination Controls and Filtering Work

The pagination interface displays Previous/Next buttons and numbered page buttons that correspond to `Math.ceil(totalUsers / itemsPerPage)` total pages. When a user clicks a page button or navigation arrow, the `fetchUsers()` callback is invoked with the target page number, along with current filter parameters to maintain search context across pagination. The component implements dynamic page size adjustment through the `handlePageSizeChange()` function, which updates `itemsPerPage`, resets to page 1, and re-fetches data with the new limit. Search filters for first name and last name trigger automatic re-fetching through a `useEffect` hook, resetting the current page to 1 whenever filter values change. The pagination controls include proper state management: the "Previous" button disables when `currentPage === 1`, and the "Next" button disables when `currentPage === Math.ceil(totalUsers / itemsPerPage)`, preventing out-of-bounds requests.

## Files Required for User Manager Page Functionality

The User Manager page requires the following frontend component files to function: [client/src/pages/UserManager.jsx](../client/src/pages/UserManager.jsx) (main page), [client/src/pages/UserUpdate.jsx](../client/src/pages/UserUpdate.jsx) (edit user form with confirmation modal), [client/src/components/Layout.jsx](../client/src/components/Layout.jsx) (page wrapper), [client/src/components/SkeletonLoader.jsx](../client/src/components/SkeletonLoader.jsx) (loading state), [client/src/components/DeleteConfirmationModal.jsx](../client/src/components/DeleteConfirmationModal.jsx) (delete confirmation), [client/src/components/UpdateConfirmationModal.jsx](../client/src/components/UpdateConfirmationModal.jsx) (update confirmation), [client/src/context/SessionContext.jsx](../client/src/context/SessionContext.jsx) (session management), and [client/src/context/ToastContext.jsx](../client/src/context/ToastContext.jsx) (notifications). The backend requires: [server/routes/user.routes.js](../server/routes/user.routes.js) (route definitions), [server/controllers/user.controller.js](../server/controllers/user.controller.js) (request handlers with pagination logic), [server/db/schemas/user.schema.js](../server/db/schemas/user.schema.js) (data validation), [server/db/connection.js](../server/db/connection.js) (MongoDB connection), and the main server file [server/server.js](../server/server.js). The UserUpdate page specifically handles user modifications via a PATCH request to `/user/:id` with confirmation via UpdateConfirmationModal before committing changes, supporting updates to first name, last name, email, occupation, location, birthdate, auth level, and optionally password fields.
